# Completion-plan unit A4.1: Run-history implementation evidence

Status: Standalone completion-plan A4.1 is accepted after code-quality, text-quality, and independent unit review. Completion-plan A4 prepared-history migration and independent PHS-06 acceptance remain pending.

## Scope and method

Agent Core completes runs after prepared history shortens. Completion-plan A4.1 precedes completion-plan A4, the prepared-history contract migration. PHS-06.2 slice A4 implements overflow recovery and has a separate scope in the [migration plan](migration-plan.md#phase-phs-062---implement-the-standard-bundled-compaction-extension).

The [technical solution](solution.md#a41-run-completion-after-prepared-history-replacement) describes the generic appended-history accounting method. `RunSummary.AddedHistory` in `host/internal/domain/agent/event.go` contains entries appended by the run. Production changes are confined to `host/internal/usecase/agent/run/service.go` and removal of the now-test-only `cloneHistory` from `host/internal/usecase/agent/run/history.go`. The helper's implementation moves unchanged to `host/internal/usecase/agent/run/clone_test.go`; its callers build mock snapshots.

Core retains the existing `HistoryStore` contract. Provider adapters, retry coordination, compaction policy, session persistence, protobuf and SDK contracts, dependencies, generated inputs, and the accepted A3 terminal-refusal implementation are unchanged.

## Public assembly regression

`TestStandardAutomaticCompactionCompletesRun` in `host/internal/app/standard_compaction_run_completion_integration_test.go` uses production application assembly, the real bundled compaction executable, SDK transport, session persistence, and the production provider adapter. The `installStandardConversationTransport` fixture in `host/internal/app/standard_compaction_automatic_integration_test.go` supplies controlled provider HTTP responses.

The test submits ten requests of 400 characters each and waits for each turn to complete. It then submits an 8,000-character request. The retained-history target is 2,000 tokens, the context window is 3,500 tokens, and the response reserve is 1,000 tokens. During the final run, the bundled extension requests automatic compaction of the older prefix.

The test checks a completed public operation and an `AgentSummary` with completed outcome and empty error text. It also checks idle run state with no active operation, one persisted compaction marker, and outgoing provider input that retains the triggering request and excludes the older repeated text. The test observes twelve provider requests: ten earlier conversation requests, one summary-generation request, and the final conversation request.

This regression uses the original compaction contract at baseline `99dcf27596b90c882e58a660bcd048f2ee9bdf58`. It requires no prepared-history migration or new production entry point. Public `AgentSummary` exposes the terminal outcome; focused Core tests inspect `RunSummary.AddedHistory` directly.

## Focused lifecycle regressions

`host/internal/usecase/agent/run/accounting_test.go` contains two tests:

- `TestRunSummaryAfterHistoryReplacement` replaces the mock prepared snapshot during provider execution. Each of its eight cases compares the entire ordered `AddedHistory` sequence with successful appends, checks the terminal outcome and applicable causes, observes awaiting-settlement state, and explicitly settles to idle.
- `TestRunSummaryOwnsDetachedEntries` checks two runs separated by settlement. The mock history store mutates transferred model content inside `Append` before returning success. The test checks that each summary retains the pre-transfer content. After both runs, it mutates the first summary and checks that storage and the second summary retain their own content. Entries independently inserted into prepared history stay outside both summaries. During message-end delivery in each run, the test attempts another run and checks rejected admission, preserved active-run state, and the final accumulated entries.

| Replacement case | Case-specific observation |
|---|---|
| `completed` | The run completes with its two appended entries. |
| `provider-failure` | The run fails with the provider cause and retains its two appended entries. |
| `cancellation` | The run aborts with `context.Canceled` and retains its two appended entries. |
| `persistence` | After the user append succeeds, the model append fails. The summary contains only the user entry; the error retains `ErrPersistenceUnavailable` and the storage cause. |
| `delivery` | Message-end delivery fails after persistence. The summary retains both entries and the delivery cause. |
| `tool-failure` | After a tool error, Core completes another model turn. The summary contains the ordered user/model/tool-result/model sequence, including the tool error result. |
| `tool-persistence` | Storage rejects the error result from a failed tool. The summary retains only the user and model entries; the error retains `ErrPersistenceUnavailable` and the original cause. |
| `terminal-delivery` | AgentEnd delivery fails. The caller receives the delivery cause; the captured summary retains completed outcome, empty error text, and both appended entries. |

In `host/internal/usecase/agent/run/settlement_test.go`, `TestCancellationBeforeFirstAppendReportsSettlement` checks empty added history, the original cancellation cause, rejected admission before settlement, and idle after explicit settlement. In `host/internal/usecase/agent/run/persistence_test.go`, `TestServiceRunStopsBeforeProviderWhenUserPersistenceFails` also checks empty added history and idle after explicit settlement.

## Test-first evidence

On 2026-10-21, the implementer ran the public regression, the ownership regression, and the original six replacement cases against baseline production code before the accounting edit:

```sh
go test -tags=integration ./host/internal/app -run '^TestStandardAutomaticCompactionCompletesRun$' -count=1 -v -timeout=90s
go test ./host/internal/usecase/agent/run -run '^TestRunSummaryOwnsDetachedEntries$' -count=1 -v
for scenario in completed provider-failure cancellation persistence delivery tool-failure; do
  go test ./host/internal/usecase/agent/run -run "^TestRunSummaryAfterHistoryReplacement$/$scenario$" -count=1 -v
done
```

Every command exited 1. The public test panicked with `slice bounds out of range [20:3]` in `Service.finish` at baseline `host/internal/usecase/agent/run/service.go:645`. The saved start position was 20, and the final snapshot contained three entries. Five focused replacement cases panicked with `[10:1]`; the persistence case panicked with `[10:0]`. The ownership test failed because the first summary contained three entries, including the independently inserted prepared-history entry, where only two belonged to the run.

Earlier setup attempts failed compilation because of test literal and import mistakes. Those attempts are excluded from behavioral RED evidence. No production file changed until the compiling RED runs above completed.

After the production edit, the implementer ran the initial GREEN checks. Both commands exited 0:

```sh
go test -race ./host/internal/usecase/agent/run -count=1 -v
go test -race -tags=integration ./host/internal/app -run '^TestStandardAutomaticCompactionCompletesRun$' -count=1 -v -timeout=90s
```

The Core package suite and public regression passed without focused-test skips.

The ownership assertion was then strengthened to mutate transferred content synchronously inside `Append`. A negative control delayed the accounting clone until after `Append` returned. `TestRunSummaryOwnsDetachedEntries` exited 1 because it observed `owner mutation` where the pre-transfer value was required. The production source remained unchanged during this control. The strengthened test passed against the implementation. The first-user persistence regression also gained explicit empty-summary and idle-settlement assertions; these preserve baseline behavior.

```sh
go test -race ./host/internal/usecase/agent/run -run 'TestRunSummary|TestServiceRunStopsBeforeProviderWhenUserPersistenceFails|TestCancellationBeforeFirstAppendReportsSettlement' -count=1 -v
```

This focused command exited 0 after both assertion corrections. The negative control demonstrates sensitivity to clone timing. The original baseline runs establish test-first order for the production fix.

After implementation, the code-quality reviewer added `tool-persistence` and `terminal-delivery`, bringing the replacement table to eight cases, and added active-run admission assertions to the ownership test. The reviewer checked these assertions with three negative controls:

| Deliberate defect in the build overlay | Focused test | Observed failure, exit 1 |
|---|---|---|
| Reset accounting before checking run admission | `TestRunSummaryOwnsDetachedEntries` | The summary contained zero entries where two were required. |
| Include a tool result after storage rejects its append | `TestRunSummaryAfterHistoryReplacement/tool-persistence` | The summary contained three entries where only two appends had succeeded. |
| Discard the AgentEnd delivery error | `TestRunSummaryAfterHistoryReplacement/terminal-delivery` | The caller received nil where the original delivery cause was required. |

The focused race command above then passed with all eight cases and the admission assertions. These post-implementation controls supplement the original six-case baseline RED run. They establish assertion sensitivity for behavior the production implementation already provided. During each control, the reviewer used a temporary build overlay and left production source unchanged.
